# 05 通知系统设计

> 目标:规范化、分类明了、层次清晰。核心是一条**五层管线**,通知对象在管线中单向流动、全程留痕。

## 1. 分类体系(层次分明的第一层)

| 分类(category) | 说明 | 默认渠道 | 示例 |
|---|---|---|---|
| comment | 互动类 | in_app + email | 新评论、评论回复、待审核 |
| system | 系统类 | in_app | 插件失败、存储告警、版本更新 |
| content | 内容类 | in_app + webhook | 文章发布、被引用 |
| digest | 摘要类 | email | 每周汇总、未读聚合 |

- 分类是枚举 + 数据库字典,插件可注册新分类(须声明默认策略)。
- 每条通知**必属一个分类**,偏好路由、模板组织、后台列表筛选都按分类分层。

## 2. 五层管线总览

```
① Ingest 接入     幂等入库            → status: ingested
② Route   偏好路由 三层偏好+静默+直通   → status: routed
③ Render  渲染     按渠道+locale 定稿   → status: rendered / render_failed
④ Deliver 投递     适配器+退避+降级链    → status: delivery_attempted / delivered / failed
⑤ Observe 观测     状态机留痕+死信       → status: dead_lettered
```

## 3. ① 事件接入(Ingest)

来源:内核钩子(`post.published` 等)、PSR-14 事件、外部 API 调用。

```php
$notification = $pipeline->ingest(new NotifyRequest(
    eventId:   'uuid-v7',        // 幂等键:同 eventId 重复提交直接返回已有记录
    dedupKey:  'comment:123:approved',  // 业务去重:同 key 在窗口期内合并
    category:  'comment',
    recipient: userId | 'role:admin' | 'broadcast',
    locale:    'zh-CN',
    payload:   ['comment_id' => 123, ...],
));
```

- 接入层只做校验与落库,不查偏好、不渲染 —— 保证业务事务快速返回。
- `dedupKey` 窗口(默认 10 分钟,可配)内相同 key 的未投递通知被合并更新。

## 4. ② 偏好路由(Route)

**偏好是一等实体**:独立表 + schema 版本化,不是散落的布尔开关。

三层覆盖,优先级由低到高:

```
系统默认(NotificationPolicy per category)
  < 分类默认(用户对该 category 的整体设置)
    < 用户覆盖(用户对单类型/单渠道的设置)
```

解析结果示例:

```json
{ "recipient": 7, "category": "comment", "channels": ["in_app", "email"],
  "quiet_hours": { "start": "22:00", "end": "08:00", "tz": "Asia/Shanghai" },
  "importance": "normal" }
```

规则:
- **静默时段**:非 critical 通知延迟到窗口外投递(合并为 digest);`critical`(如安全告警)直通,无视静默。
- 渠道解析为空 → 通知仅落库为 in_app 未读(站内信永远兜底)。
- 偏好读取带请求级缓存;用户修改偏好即时生效,派发 `notification.preference.updated`。

## 5. ③ 模板渲染(Render)

- 模板按 `(templateKey, channel, locale)` 三元组查找,缺失回退链:`channel → in_app 模板 → 纯文本兜底`。
- 渲染在投递**前**完成并持久化(渲染结果存入通知记录):重试投递不重渲染,避免重复发信时内容漂移。
- 模板为受限 PHP/轻量占位符(禁止任意代码),变量来自 payload 白名单。
- 渲染失败 → `render_failed`,不再进入投递,后台可见错误详情。

## 6. ④ 投递(Deliver)

渠道适配器统一接口:

```php
interface ChannelAdapter { public function send(RenderedNotification $n, RecipientContact $to): DeliveryResult; }
```

| 渠道 | 实现要点 |
|---|---|
| in_app | 写 `notifications` 收件表,天然成功;唯一必达渠道 |
| email | SMTP(可插拔),批量经队列;退信解析回写状态 |
| webhook | POST JSON + HMAC 签名头 `X-PenBlog-Signature`;目标 URL 须用户配置并验证 |

- **指数退避**:1m → 5m → 25m → 2h → 8h(共 5 次),仅对可重试错误(网络/5xx)。
- **降级链**:email 连续失败 → 转 in_app 提醒;webhook 失败 → 保留 dead_letter 供手动重放。
- 投递节流:同一 recipient+category 每分钟上限(防轰炸),超限合并。

## 7. ⑤ 可观测(状态机)

```
ingested → routed → rendered → delivery_attempted → delivered
              │          │              │
              │          └→ render_failed│→ failed → (退避重试) → dead_lettered
              └→ suppressed(偏好关闭/去重合并)
```

- 状态变更全部落 `notification_events` 追加日志(谁、何时、何渠道、结果),后台可按 eventId 查完整轨迹。
- `dead_lettered` 进死信列表,支持一键重放/丢弃;死信保留 30 天。
- 指标:各分类量、各渠道成功率、平均延迟 —— 后台通知健康面板。

## 8. 站内信存储(性能设计)

```sql
notifications(id, recipient_id, category, template_key, title, body_html,
              read_at, archived_at, created_at)
-- 复合索引 (recipient_id, created_at DESC);软删除用 archived_at,不物理删
```

- 未读计数走覆盖索引;超 90 天的已读已归档记录可清理(任务化)。

## 9. API 面(摘要,详见 06)

```
GET/PUT  /api/v1/notifications/preferences            # 偏好(一等实体,schemaVersion)
GET      /api/v1/notifications                        # 我的站内信(分页+filter[category])
POST     /api/v1/notifications/{id}:read              # 标记已读
GET      /api/v1/notifications/traces/{eventId}       # 轨迹(管理员)
POST     /api/v1/webhooks                             # 出站 webhook 订阅(事件类型订阅)
```

## 10. 扩展点

- 插件可注册:新分类、新模板、新渠道适配器(`ChannelRegistry`)、订阅出站 webhook 事件。
- 内核保证:未安装任何插件时,comment/system/content/digest 四类与三渠道全部可用。
